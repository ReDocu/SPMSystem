## 1. 개요

### 1.1 정의

1인 사용자 전용 개인 관리 도구. 일정, 프로젝트, 운영·배포, 자료수집을 하나의 시스템에서 관리한다.

### 1.2 목적

실제로 매일 사용하는 도구를 만드는 것. 포트폴리오용이 아니라 실사용이 목적이므로, 기능의 완결성보다 **사용 지속성**이 우선한다.

### 1.3 핵심 가치

> 내 모든 일과 프로젝트를 한 곳에서, 마찰 없이 기록하고 꺼내본다.

### 1.4 설계 철학

개인 도구는 기능이 부족해서가 아니라 **기록하기 귀찮아서** 죽는다. 따라서 다음을 최우선으로 둔다.

1. **입력 마찰 최소화** — 어디서든 3초 안에 기록할 수 있어야 한다
2. **연결성** — 4개 영역이 데이터를 공유한다. 프로젝트 마일스톤이 일정에 뜨고, 배포 이력이 프로젝트에 쌓인다
3. **조용함** — 알림은 하루 한 번. 배지는 주의가 필요할 때만
4. **탈출 가능** — 언제든 내 데이터를 통째로 꺼낼 수 있다

## 2. 사용자 및 범위

### 2.1 사용자

단일 사용자(개발자 본인). 다중 사용자 시나리오는 고려하지 않는다.

### 2.2 구현하지 않는 것

1인 전용이므로 아래는 명시적으로 범위에서 제외한다. 이것만으로 개발량이 절반 가까이 줄어든다.

| 제외 항목 | 사유 |
|---|---|
| 회원가입 페이지 | 계정 1행을 마이그레이션으로 생성. 인증은 로컬 PIN 하나면 충분 |
| 소셜 로그인 · OAuth | 로컬 전용으로 전환하며 제거 (v0.3 결정) — 외부 IdP 의존 없음 |
| 권한 · 역할 · 초대 | 사용자가 한 명 |
| 공유 · 댓글 · 멘션 | 협업 대상이 없음 |
| 담당자(assignee) 필드 | 항상 본인 |
| 동시성 처리 · 낙관적 락 | 충돌할 사람이 없음 |
| 알림 인박스 UI | Discord Webhook으로 대체 |

여기서 아낀 리소스는 **입력 속도, 검색, 모바일 캡처**에 투입한다.

## 3. 정보 구조 (IA)

### 3.1 전체 구조

```
로그인
  └ 메인 (4분할 런처)
       ├ 일정 관리      /schedule
       ├ 프로젝트 관리   /projects
       ├ 운영 · 배포     /ops
       └ 자료 수집      /resources
     (공통) 인박스       /inbox
     (공통) 설정        /settings
```

메인은 대시보드가 아니라 **어느 기능 페이지로 갈지 결정하는 런처**다.

### 3.2 라우팅

```
/login
/                      메인 런처
/schedule              일정 → 오늘 일별 뷰로 리다이렉트
  /schedule/day/:date
  /schedule/month/:yyyy-mm
  /schedule/year/:yyyy
/projects              프로젝트 목록
  /projects/:id        상세 (탭: 개요 / 태스크 / 문서 / 회고)
/ops                   운영 · 배포 (대시보드)
  /ops/platforms
  /ops/environments
  /ops/deployments
  /ops/incidents
  /ops/costs
/resources             자료 수집
  /resources/:id
/inbox                 미분류 캡처
/settings
```

### 3.3 네비게이션

메인 런처는 로그인 직후 관문 역할을 하되, 기능 페이지 내부에서는 **사이드바를 상시 노출**해 영역 간 이동에 메인을 거치지 않게 한다.

> **확정** — 좌측 사이드바 상시 노출. 항목: 4개 영역 + 인박스 + 설정.

## 4. 관통 컨셉: 인박스

### 4.1 개념

일정이든 아이디어든 링크든, **일단 한 곳에 던져 넣고 분류는 나중에.** 4개 페이지가 각자 입력 폼을 갖는 대신 전역 캡처 하나가 모든 입력을 받는다.

```
Cmd+K → 한 줄 입력 → 저장 끝
         ↓ (나중에 인박스에서 처리)
         할 일 / 아이디어 / 자료 / 프로젝트 태스크
```

### 4.2 자동 추정 규칙

| 입력 패턴 | 추정 결과 |
|---|---|
| URL로 시작 | 자료 |
| "내일", "금요일" 등 | 할 일 + 날짜 파싱 |
| `#프로젝트명` 포함 | 해당 프로젝트 태스크 |
| 코드 블록 형식 | 코드 스니펫 |
| 날짜 없이 시간 범위 (`14-16 SPM 개발`) | 오늘 타임로그 |
| 미래 날짜 + 시간 범위 (`내일 14-16 회의`) | 일정(event) — 날짜 규칙 우선 |
| 그 외 | 아이디어 |

추정이 틀려도 인박스에서 한 번에 정리하면 되므로 부담이 없다.

### 4.3 처리 UX 원칙

- 항목당 **클릭 1~2회**로 처리 완료. 3회를 넘으면 인박스가 쌓이기만 한다
- 추정에 확신이 있으면 기본 버튼 1개 + 탈출구 1개, 애매하면 4개 전부 노출
- 파싱 결과를 원문에 인라인 표시 (`내일` 옆에 실제 날짜 배지). 없으면 "제대로 인식했나" 불안이 남는다
- `E` `A` `P` `I` 키보드 단축키 지원
- 캡처 출처 기록 (웹 / 북마클릿 / 모바일) — 어느 경로가 방치되는지 파악용
- 삭제는 **5초 되돌리기 토스트** 제공
- 처리 후 0.3초 페이드 아웃
- **저장 실패(세션 만료·오프라인) 시 로컬 큐에 보관 후 자동 재시도** — 캡처 유실은 마찰 최소화 철학의 최대 리스크

### 4.4 수집 경로

개발 난이도 순.

1. 웹 앱에서 붙여넣기
2. **북마클릿** — `javascript:` 한 줄로 현재 페이지를 POST. 크롬 확장보다 훨씬 쉽고 효과는 대부분 동일
3. 크롬 확장 (후순위)

## 5. 페이지별 기획

### 5.1 메인 런처

#### 구성

2×2 타일 그리드 + 하단 빠른 입력창 + 인박스 카운트.

각 타일은 아이콘, 영역명, 상태 요약 1~2줄, 배지로 구성한다.

#### 타일별 표시 정보

| 타일 | 메인 숫자 | 서브 라인 | 배지 조건 |
|---|---|---|---|
| 일정 관리 | 오늘 남은 할 일 | 다음 일정 시각 | 마감 지난 항목 존재 |
| 프로젝트 관리 | 진행 중 프로젝트 수 | 최근 활동 프로젝트 + 진행률 | 마감 지난 프로젝트 태스크 존재 |
| 운영 · 배포 | 운영 중 서비스 수 | 헬스체크 상태 / 최근 배포 | 다운, 만료 D-7 |
| 자료 수집 | 이번 주 수집 수 | 아이디어 수 | 인박스 10건 초과 |

#### 배지 규칙

| 색상 | 의미 |
|---|---|
| 🔴 빨강 | 지금 조치 필요 (서버 다운, 오늘 마감 미완료) |
| 🟡 노랑 | 1주 내 처리 (SSL·결제 만료 D-7) |
| 없음 | 정상 |

**항상 켜져 있으면 아무것도 안 켜진 것과 같다.** 정상 상태에서는 배지가 대부분 비어 있어야 한다.

#### 설계 노트

- 지연 항목은 배지뿐 아니라 목록 안에 빨간 텍스트로 직접 표시 — 클릭 전에 판단 가능
- 진행률 바는 얇게(4px). 숫자만으로는 비교가 안 되고, 두꺼우면 타일이 무거워진다
- 빠른 입력창은 타일 아래에 배치. 시선 흐름이 "상황 파악 → 그래서 뭘 던져넣을까"로 끝난다

#### 확정 사항

- 클릭 동작은 **하이브리드** — 타일 전체 클릭은 영역 이동, 타일 안의 개별 항목(지연 태스크 등)은 해당 상세로 딥링크
- 서브 라인에 다 못 싣는 항목은 **최근 활동순**으로 노출

### 5.2 개인 일정 관리

상세 기획은 **일정관리-상세기획.md (v0.2)** 로 확정. 핵심 요약:

- **3뷰 구조**: 일별(기록지 — 타임로그가 메인) / 달별(프로젝트 현황판 — 기록 요약이 주인공, 일정은 레이어) / 연별(연차별 목표 TO DO LIST + 기념일)
- **데일리 루틴 등급화**: 필수 타임로그 / 권장 할 일 체크·인박스 캡처 / 선택 데일리 노트·컨디션 1탭. **타임로그만 채우면 그날 의무 끝**
- **일정 카테고리**: 일반 / 기념일 / 출장 / 수업. `rrule` 반복 + 단일 회차 취소·변경(EXDATE)
- **백로그**: 별도 페이지 없이 일별 우측 패널 접이식 섹션. 오늘로 끌어오기 = `planned_date` 지정
- **개념 분리 확정** (미결정 #1 → B): task(완료 개념) / event(시간 점유) / log(지나간 시간의 기록)

### 5.3 개인 프로젝트 관리

상세 기획은 **프로젝트관리-상세기획.md (v0.1)** 로 확정. 핵심 요약:

- **생애주기 게이트**: 상태 전이 시점마다 정리 항목을 붙인다 — G0 씨앗(등록) → G1 킥오프(목적·타겟·범위·스택 후보) → G2 개발 시작(저장소·마일스톤·첫 태스크) → G3 플랫폼 선정(배포 플랫폼·운영 핸드오프) → G4 회고
- **소프트 강제**: 전이 시 게이트 카드를 제시하되 건너뛰기 가능. 개요 탭에 채움도 표시
- **목록**: 관리 그룹 4개 — 진행중 / 대기중 / 완료 / 폐기. `idea`는 대기중 소속의 아이디어 풀 (별도 아이디어 인박스 없음 — 전역 인박스 일원화)
- **생애 타임라인**: 개요 탭 상단, 간트형 상태 구간 바 + 마일스톤·배포 마커. 입력 없이 자동 생성 (`project_events`)
- **상세 탭 4개**: 개요 / 태스크(칸반+마일스톤) / 문서(마크다운 목록 + 템플릿 4종) / 회고(4문항 + 자동 수치)
- **GitHub 연동**: 읽기 전용 (v0.6)
- 진행률 계산: 마일스톤 가중 평균, `dropped` 분모 제외, 서버 캐싱 (상세 문서 §4)

### 5.4 프로젝트 운영 · 배포 관리

상세 기획은 **운영배포-상세기획.md (v0.1)** 로 확정. 핵심 요약:

- **컨셉**: 시스템은 안내와 기록만 하고, 판단은 사람이 한다. 시크릿 값은 저장하지 않는다 — 메타데이터만. 가격도 자동 수집하지 않는다
- **플랫폼 카탈로그**: 시드 4개 카테고리(웹·클라우드 / 게임 / 모바일 스토어 / 도메인·구독) + 직접 추가. G3 게이트의 플랫폼 선택도 여기서
- **가격 체크 3단계**: [가격 페이지 열기] 링크 제공 → 직접 확인·입력 → 확인 저장(`price_checked_at`). 90일 경과 시 흐림 표시, 갱신 D-7 알림에 재확인 딥링크. 통화는 통화별 그대로 기록, 합계 병기
- **환경 관리**: dev/staging/prod, 도메인·SSL 만료, 플랫폼 연결
- **배포 이력 + 체크리스트**: 템플릿 + 배포 시 스냅샷 저장. 수동(v0.5) → Vercel Webhook 반자동(v0.6). 배포는 프로젝트 생애 타임라인의 ▲ 마커
- **모니터링·장애**: 헬스체크는 UptimeRobot 위임(다운 알림 Discord 직행), 장애 기록은 발생→원인→조치→재발방지
- **비용**: 무료 티어도 0원 등록 — "지금 뭘 쓰고 있나" 인벤토리 역할

### 5.5 자료 수집

상세 기획은 **자료수집-상세기획.md (v0.1)** 로 확정. 핵심 요약:

- **v1은 2종만**: 사이트 모음(카테고리별 링크) + 아이디어(메모). 작게 시작하고 추후 업데이트로 키운다
- **카테고리**: 단일 필드, 기본 4종(디자인/개발/기획/기타) + 사용자 추가. 태그는 별도 공통 레이어
- **URL 메타데이터 자동 추출**은 v1 유지 — 붙여넣으면 `og:title`·썸네일 자동 채움
- **인박스 "아이디어" 처리의 종착지** — 프로젝트 아이디어는 프로젝트 `idea`로, 일반 아이디어는 여기로 분기
- **추후 업데이트 풀** (버전 미배정): 코드 스니펫, 파일·이미지, 본문 아카이빙, 읽기 큐, `tsvector` 전문 검색, 프로젝트 N:M 연결

## 6. 상태값 정의

```
Task      todo → doing → done
                       ↘ dropped

Project   idea → planning → active → live → completed
                              ↕
                            paused
          (어느 상태에서든 ↘ dropped — 폐기, 회고를 거침)

Resource  (v1은 상태 없음 — 읽기 큐 도입 시: unread → reading → done ↘ archived)
```

### 설계 노트

- **`dropped`는 반드시 둔다.** 안 할 일을 지우지 않고 남겨두면 "내가 뭘 포기했나"가 회고 자료가 된다
- **`active`와 `live`를 분리한다.** 운영·배포 페이지는 `live` 상태만 다루면 되므로 화면이 자동 정리된다
- **프로젝트 종착은 `completed`(완주)와 `dropped`(폐기)로 분리한다.** 화면의 관리 그룹은 4개 — 진행중(active·live) / 대기중(idea·planning·paused) / 완료 / 폐기
- `blocked`, `review` 같은 상태는 1인 도구에서 의미가 없으므로 두지 않는다

```
                   category, exdates[]

time_logs          id, date, start_min, end_min, content,
                   project_id?, task_id?

daily_notes        id, date, content, condition?    -- (user_id, date) unique

inbox_items        id, raw_text, source, guessed_type, processed_at

resources          id, type, url?, title, memo, content?,
                   thumbnail?, category?      -- v1: site | idea

platforms          id, name, category, homepage_url, pricing_url,
                   free_tier_note, is_custom

environments       id, project_id, name, platform_id?, host, domain,
                   ssl_expires_at

deployments        id, environment_id, version, deployed_at,
                   changelog, rolled_back, checklist_snapshot(json)

checklist_templates id, project_id?, name, items(json)

incidents          id, project_id, occurred_at, cause, action, prevention

costs              id, project_id?, platform_id?, name, amount, currency,
                   cycle, next_billing_at, price_checked_at

tags               id, name, color
taggables          tag_id, target_type, target_id      -- 다형 태그
```

### 규칙

1. **`tasks.project_id`는 nullable.** 프로젝트에 속하지 않는 개인 할 일("병원 예약")도 같은 테이블에서 다뤄야 캘린더 통합이 깔끔하다
2. **모든 테이블에 `user_id`를 넣는다.** 지금은 혼자여도, 없으면 나중에 어떤 변경이든 마이그레이션이 지옥이 된다
3. **태그와 전역 검색은 처음부터 공통 레이어로 설계한다.** 나중에 붙이면 고생한다

## 8. 기술 스택

> **v0.3 변경 (2026-08-28)** — 클라우드(Vercel + Supabase) 전제를 버리고 **로컬 실행**으로
> 전환한다. 1인 도구에 외부 의존을 없애고, 데이터를 내 머신에 둔다.

```
Next.js (App Router) + TypeScript   로컬 실행 (npm run dev / start)
  └ 로컬 Postgres          데이터 저장 (pg 클라이언트, DATABASE_URL)
  └ PIN 인증               간단 잠금 (환경변수 PIN + 서명 쿠키)
  └ Discord Webhook        알림 수신 (선택)
  └ pg_dump + JSON export  백업
```

구버전 스택(Vercel Hobby + Supabase + UptimeRobot)의 제약 대응(§8.1)은 폐기한다.
원격 배포가 다시 필요해지면 그때 별도 결정한다.

### 8.1 로컬 운영 노트 (v0.3 개정 — 구 플랫폼 제약 표 폐기)

| 항목 | 내용 |
|---|---|
| 실행 | 내 PC에서 `npm run dev` / `npm start`. 앱이 꺼져 있으면 캡처도 안 되므로 부팅 시 자동 실행 등록 권장 |
| DB | 로컬 Postgres (`DATABASE_URL`). 클라우드 무활동·용량 제약 없음 |
| 일일 요약 | Vercel Cron 대신 로컬 스케줄러(Windows 작업 스케줄러 / cron)에서 `/api/cron/daily` 호출 |
| 백업 | JSON export(앱 내) + `pg_dump`(스케줄러). 백업이 전적으로 본인 책임인 점은 동일 |

### 8.2 필수 준수 사항

1. **PIN 인증을 켠다.** 로컬이라도 같은 네트워크에서 접근될 수 있다. 환경변수 PIN + 서명 쿠키(HMAC)면 충분 — 계정·소셜 로그인은 두지 않는다 (v0.3 결정)
2. **이미지는 업로드 시 WebP로 리사이즈·압축한다.** 로컬 디스크라도 무한하지 않다
3. **외부 썸네일은 원본 URL을 직접 참조한다.** 서버에 복사하지 않는다
4. **JSON export 버튼을 v0.1부터 유지한다.** 백업이 전적으로 본인 책임이다.
   범위는 **DB 텍스트 전체 (Storage 파일 제외)** — 설정 화면에 명시 고지

### 8.3 성능 규칙

- 메인 화면은 `GET /api/summary` **한 번**으로 4개 타일 데이터를 모두 받는다. 타일별 개별 호출 시 로그인 직후 화면이 덜컹거린다

## 10. 빈 화면 (Empty State)

처음 켰을 때가 가장 중요한데 보통 기획에서 누락된다.

| 화면 | 메시지 | 액션 |
|---|---|---|
| 메인 | 타일에 "아직 없음" | 첫 항목 추가 유도 |
| 일별 | (빈 슬롯 자체가 UI — 별도 메시지 없음) | 첫 방문에만 "빈 칸을 눌러 기록해보세요" 힌트 1회 |
| 달별 | "이번 달 기록이 없습니다" | 오늘 기록지로 이동 유도 |
| 연별 | "올해 하고 싶은 일을 적어보세요" | 입력 포커스 |
| 프로젝트 | "첫 프로젝트를 만들어보세요" | 생성 버튼 강조 |
| 인박스 | "인박스가 비었습니다 ✨" | (긍정 메시지) |
| 자료 | "북마클릿을 설치해보세요" | 설치 안내 |

**인박스가 비었을 때만 축하 메시지를 쓴다.** 다른 곳은 생성 유도. 인박스는 비우는 것이 목표이기 때문이다.

**최초 로그인 온보딩 (1회)** — 빈 런처만으로는 무엇부터 할지 알 수 없다 (USE-03).
3단계 가이드: ① 오늘 타임로그 1칸 기록 → ② ⌘K로 캡처 1건 → ③ 북마클릿 설치 안내.
완료하거나 건너뛰면 다시 노출하지 않는다.

## 11. UX 공통 요구사항

1인용 도구는 속도가 생명이다.

- **커맨드 팔레트** (`Cmd+K`) — 빠른 입력과 페이지 이동을 모두 처리
- 키보드 단축키 전반
- 다크모드
- 모바일 PWA — 홈 화면 아이콘, 공유 시트로 캡처 창 직행
- **모바일 캡처 진입점**: 하단 고정 [+] FAB → 캡처 시트 — ⌘K의 모바일 대체. 없으면 "3초 캡처"가 모바일에서 무너진다 (ISSUE-03)
- 모바일 메인은 2×2 그리드 유지 (세로 4개 스택보다 엄지 도달 범위에 유리)
- **미구현 버전의 메뉴·탭은 숨긴다** (비활성 표시가 아니라 숨김) — 빈 껍데기 노출 금지 (ISSUE-11)
